# ucspecの現状理解

bizspecの出発点とした [ucspec](https://github.com/nuitsjp/ucspec) についての理解です。

> **注意**
> この文書は、2026-11-11時点のucspecのREADMEだけをもとにしています。docs配下の文書とソースコードは読んでいません。設計を進める前に、状態定義モデル、記述ガイド、網羅率と保証範囲、アーキテクチャの各文書を確認する必要があります。

## 位置づけ

ucspecは、利用者の目的を中心に、仕様・シナリオ・網羅性を一緒に育てるためのGo製CLIです。顧客との接点を持つ開発者のユースケース駆動開発を支援します。

## 仕組み

- プロダクト内で一元管理した状態遷移モデルを、複数のユースケースが参照する。
- 人とAIが、構造化した仕様（JSON・YAML）を編集する。
- 決定論的な検査器が、次のことを検査する。
  - 状態の構造の整合性
  - シナリオの成立
  - ユースケースの完了可能性
  - シナリオの定義網羅率
- 結果を、図とシナリオを行き来できる自己完結型のHTMLへ出力する。

## 設計原則

- 開発はユースケースの目的から始める。画面遷移図を先に完成させて分解する方式ではない。
- 同じ画面・状態・イベントをユースケースごとにコピーしない。共有する論理画面は一度だけ定義する。
- 図、シナリオ表、網羅率は正本データから生成する。生成したHTMLを直接編集しない。
- 意図した振る舞い・禁止事項・期待結果は、モデルと独立に記述する。AIが候補を自動承認する方式ではない。
- AIは編集を支援するが、検査・生成の実行にAIサービスは必要ない。

## 主な機能

| 分類 | 内容 |
|---|---|
| 仕様の記述 | JSON・YAML、JSON Schema、名前による参照、アクター、入れ子の状態、状態に書くイベント、名前付き分岐のディシジョン、ネスト可能なユースケースパッケージ |
| シナリオ | イベントと分岐名による手順、目的と期待結果の記述 |
| シナリオ検査 | アクターの権限、範囲、ユースケースの終了 |
| 構造検査 | 名前と参照、開始、ディシジョン、完了可能性、到達できない状態・遷移の警告 |
| 網羅率 | 末端状態、複合状態、遷移、連続2遷移、プライムパス、上限付き完了パス |
| 未網羅の評価 | シナリオの追加・既存シナリオでの代表・禁止の判断と理由、設計要求 |
| 回帰・変更影響 | ユースケース横断の回帰、過去のレポートとの差分 |
| 仕様書 | 自動配置したSVGの図、全体図・ユースケース別図・複合状態の内部図、シナリオと未網羅経路の強調 |

## 対象外としているもの

- 実アプリのE2Eテストの生成・実行・対応付け
- データの中身と業務の論理の検証
- 顧客との合意状態の管理
- 並行領域、履歴状態、入場・退場アクション
- 必然的終了の証明

## bizspecとの差分

| 観点 | ucspec | bizspec |
|---|---|---|
| 視点 | ユースケース | 業務全体 |
| 対象とする作業 | ユーザー操作を伴う作業 | ユーザー操作を伴う作業、サービス作業、マニュアル作業 |
| モデル | ステートマシン | ビジネスワークフロー、ステートマシン、アクティビティ |
| 並行 | 対象外 | ビジネスワークフローで受け入れる |
| テストケース | 生成は対象外 | モデルから構築する |
| データ | 持たない | ビジネスオブジェクトを導出する（記述範囲は未決） |
| 束ねる単位 | ユースケース | 作業（ユースケースの扱いは再検討中） |
