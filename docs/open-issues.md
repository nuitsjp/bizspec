# 未決事項

これから決める必要がある事項です。設計への影響が大きいものから並べています。

## スコープに関わる事項

### O-01 ucspecを内包する方法

ucspecを内包することは確定しています（D-03）。方法は決めていません。

- ucspecのリポジトリーを拡張するか、bizspecが別のツールとしてucspecを取り込むか。
- モデルのファイルを1つにまとめるか、レイヤーごとに分けるか。
- ucspecの既存のモデル（ユースケース、範囲など）を、作業の概念へどう移行するか。

### O-02 実テストとの対応付け

現在の決定事項で評価できるのは、モデルに対するシナリオ定義の網羅性です。実際のテストとの対応付けや、実行結果の取り込みを含めるかどうかを決める必要があります。

ucspecは、E2Eテストの生成・実行・対応付けを対象外にしています。含めない場合、「テストの品質を評価する」という表現は実態より強くなります。

### O-03 テストケースとして出力するもの

モデルからテストケースを構築することは、当初からの要求です。出力するものの水準を決めていません。

- 手順と期待結果からなる抽象テストケースまでか。
- 具体的なテストデータや、実行可能なテストコードまでか。

属性を持たない場合、具体的なテストデータはツールから生成できません。

## モデルに関わる事項

### O-04 並行を含む網羅率の定義

並行を受け入れることは確定しています（D-12）。網羅率の定義は提案の段階です（P-10）。

### O-05 種別をまたぐinclude・extendの接続

種別をまたぐ関係を認めることは確定しています（D-15）。ステートマシンからアクティビティを呼ぶ場合に、どの遷移で呼び、結果をどう受け止めるかの定義が必要です。

### O-06 サービス作業の機能仕様

アクティビティ図で表すことは確定しています（D-10）。画面を持たないため、次の書き方を決める必要があります。

- 起動契機（時刻、イベントなど）
- 事前条件
- 結果の分岐

### O-07 アクティビティに対する検査と網羅率

サービス作業とマニュアル作業の内部はアクティビティです。ucspecの検査はステートマシンを対象にしているため、アクティビティに対する検査と網羅率を定義する必要があります。

### O-08 マニュアル作業の検証

マニュアル作業はシステムの実装を持ちません。内部のアクティビティに対するシナリオと網羅率を、何の根拠として使うのか（運用リハーサルなど）を決める必要があります。

### O-09 ビジネスオブジェクトの記述範囲

状態を持ち、属性を持たない案が出ています（P-02）。決定していません。

- 属性を、検査に使わない説明項目として書けるようにするか。
- 外部のデータモデルへの参照を持たせるか。

### O-10 ユースケースという概念の扱い

作業に統合する方向で検討が進んでいます（A-02）。明示の決定はありません。

- モデル要素としてのユースケースを廃止するか。
- 「ユースケース」という言葉を、生成ビューの名前として残すか。

### O-11 作業の定義と出現の分離

同じ作業を複数の箇所で使うための仕組みです（P-04）。include・extendとの役割分担を含めて決める必要があります。

### O-12 用語の確定

- 「ユーザー作業」は仮称です。
- 「反映確認フロー」は仮称です。

## 実現方法に関わる事項

### O-13 モデルの記述形式

ucspecはJSON・YAMLとJSON Schemaを使っています。bizspecの形式は決めていません。アクティビティと並行をどう書くかが論点になります。

### O-14 生成するビュー

次のようなビューが候補です。一覧と優先順位は決めていません。

- 業務フロー図
- 作業ごとの内部図（ステートマシン、アクティビティ）
- ビジネスオブジェクトのライフサイクル図
- 作業とビジネスオブジェクトの対応表
- シナリオと未網羅経路の一覧

### O-15 実装技術と配布形態

ucspecはGo製のCLIです。bizspecの実装言語、配布形態、対応プラットフォームは決めていません。

### O-16 名称の重複確認

bizspecという名称が、既存のツール、パッケージ、商標と重複していないかを確認していません。
